# ניהול גרסאות, Git ו-GitHub עם Claude Code

בפרקים הקודמים ביקשנו מ-Claude שוב ושוב "תשמור את המצב הנוכחי ב-git", והבטחנו להסביר בהמשך. הגיע הזמן.

**Git** הוא כמו כפתור "שמירת משחק" לפרויקט שלכם. בכל פעם ששומרים, Git זוכר בדיוק איך נראה כל קובץ באותו רגע. אם משהו נשבר אחר כך, אפשר לחזור לכל נקודת שמירה קודמת. **GitHub** הוא אתר ששומר עותק של הפרויקט בענן, כדי שלא ילך לאיבוד, כדי שתוכלו לשתף אותו עם אחרים, וכדי שאפשר יהיה להעלות אותו לאוויר (פרק 9).

החדשות הטובות: לא צריך לזכור פקודות Git. Claude מכיר אותן מצוין. אתם צריכים להבין **מה** אתם רוצים, ו**ממה** להיזהר.

<Callout type="note" title="מה תלמדו בפרק">
- המושגים הבסיסיים של Git, בשפה פשוטה.
- לבקש מ-Claude ליצור ענפים, להראות מה השתנה ולכתוב הודעות שמירה מסודרות.
- להעלות פרויקט ל-GitHub, לפתוח Pull Request ולקבל סקירת קוד.
- **חגורות בטיחות**: איך מונעים פקודות הרסניות כמו `git push --force` ומגינים על הענף הראשי.
</Callout>

## מילון קצר

| מושג | באנגלית | מה זה, בפשטות |
| --- | --- | --- |
| **מאגר** | Repository (Repo) | תיקיית פרויקט ש-Git עוקב אחריה |
| **שמירה** | Commit | נקודת שמירה עם הודעה קצרה שמתארת מה השתנה |
| **ענף** | Branch | עותק מקביל של הפרויקט שבו אפשר לנסות דברים בלי לגעת בגרסה הראשית |
| **הענף הראשי** | main | הגרסה ה"רשמית" של הפרויקט, זו שעולה לאוויר |
| **הבדלים** | Diff | רשימה של מה בדיוק השתנה: שורות שנוספו ושורות שנמחקו |
| **מאגר מרוחק** | Remote | העותק של הפרויקט ב-GitHub |
| **דחיפה** | Push | שליחת השמירות מהמחשב שלכם ל-GitHub |
| **משיכה** | Pull | הורדת שינויים מ-GitHub למחשב שלכם |
| **בקשת מיזוג** | Pull Request (PR) | הצעה רשמית לאחד ענף לתוך main, עם אפשרות לסקור ולהגיב לפני האיחוד |
| **מיזוג** | Merge | איחוד השינויים מענף אחד לתוך ענף אחר |

<Callout type="tip" title="ענף זה כמו טיוטה">
דמיינו מסמך חשוב. במקום לערוך את המקור, עושים עותק, מנסים בו שינויים, ורק כשהם טובים מעתיקים אותם למקור. ענף ב-Git הוא בדיוק העותק הזה, ו-main הוא המקור.
</Callout>

### אומרים ל-Git מי אתם

כל שמירה ב-Git חתומה בשם ובאימייל. את זה מגדירים **פעם אחת** במחשב. עשו את זה בעצמכם, בטרמינל רגיל, עם הפרטים שלכם:

```bash title="בכל מערכת הפעלה"
git config --global user.name "השם שלכם"
git config --global user.email "your-email@example.com"
```

<Callout type="info" title="איזה אימייל?">
אם תשתמשו ב-GitHub, כדאי להשתמש באותו אימייל שאיתו תירשמו לשם. השם והאימייל יופיעו ליד כל שמירה, וגם יהיו גלויים לכל מי שרואה את הפרויקט אם הוא ציבורי.
</Callout>

## חלק 1: שמירות והודעות מסודרות

### מתחילים מאגר

פרויקט Next.js (כמו בפרק 6) כבר מגיע עם Git. בכל פרויקט אחר, בקשו:

<Prompt>תאתחל git בתיקייה הזאת, תוודא שיש קובץ .gitignore מתאים לפרויקט (בלי node_modules ובלי קבצי .env), ותשמור את המצב הנוכחי כנקודת התחלה</Prompt>

<Callout type="warning" title="מה זה .gitignore ולמה הוא חשוב?">
`.gitignore` הוא רשימה של קבצים ש-Git **לא** ישמור. שני דברים חייבים להיות בה: `node_modules` (אלפי קבצים שאפשר תמיד להתקין מחדש) וקבצי `.env`, שבהם שומרים סיסמאות ומפתחות. מפתח שנשמר ב-Git ועלה ל-GitHub צריך להיחשב כאילו נחשף, גם אם מחקתם אותו אחר כך.
</Callout>

### "מה השתנה?"

לפני ששומרים, תמיד כדאי לדעת מה הולך להישמר:

<Prompt>מה השתנה מאז השמירה האחרונה? תסכם לי בעברית, קובץ אחרי קובץ, במשפט אחד לכל קובץ</Prompt>

מאחורי הקלעים Claude יריץ פקודה כמו `git status`. ככה נראה הפלט שלה:

```text title="git status (פלט לדוגמה)"
On branch main
Changes not staged for commit:
        modified:   app/page.tsx
        modified:   lib/recipes.ts

Untracked files:
        components/SearchBar.tsx
```

`modified` אומר שקובץ קיים השתנה, ו-`Untracked` אומר שזה קובץ חדש ש-Git עוד לא מכיר.

## חלק 2: ענפים, מקום בטוח לנסות

### למה לעבוד בענף?

נניח שאתם רוצים לנסות עיצוב חדש לגמרי לאתר. אם תעבדו ישר על main ותתחרטו באמצע, יהיה לכם בלגן. בענף נפרד, main נשאר בדיוק כמו שהוא, ואם הניסוי לא הצליח, פשוט זורקים את הענף.

**כלל אצבע:** כל פיצ'ר חדש או ניסוי, בענף משלו.

<Prompt>אני רוצה להוסיף לאתר אפשרות לסמן מתכונים כמועדפים. תיצור ענף חדש בשם feature/favorites מתוך main, תעבור אליו, ותגיד לי כשאפשר להתחיל</Prompt>

```text title="מה Claude מריץ (לדוגמה)"
$ git switch -c feature/favorites
Switched to a new branch 'feature/favorites'
```

עכשיו כל העבודה נשמרת בענף `feature/favorites`. שם הענף הנוכחי מופיע גם בפינה התחתונה של Cursor, כך שתמיד רואים איפה אתם.

<Callout type="tip" title="שמות ענפים">
נהוג להשתמש במילה באנגלית שמתארת את סוג השינוי, ואחריה תיאור קצר: `feature/favorites` לפיצ'ר חדש, `fix/search-empty-results` לתיקון באג, `design/new-colors` לניסוי עיצובי. בלי רווחים ובלי עברית.
</Callout>

### עוברים בין ענפים

<Prompt>תשמור את מה שעשינו בענף הזה, ותחזיר אותי ל-main. אני רוצה לראות שהאתר המקורי לא השתנה</Prompt>

רעננו את הדפדפן: האתר חזר למצב של main. בקשו לחזור ל-`feature/favorites`, והשינויים יחזרו. זה הקסם של ענפים.

<Callout type="warning" title="לפני שעוברים ענף: שומרים">
אם יש שינויים שלא נשמרו, Git לפעמים יסרב לעבור ענף, או יעביר את השינויים איתכם לענף השני. ההרגל הבטוח: לפני כל מעבר, "תשמור את מה שיש".
</Callout>

## חלק 3: לראות בדיוק מה השתנה

לפני שמשהו נכנס ל-main, צריך לדעת בדיוק מה הוא. יש שלוש דרכים, מהוויזואלית לטקסטואלית:

**1. Source Control ב-Cursor** (`Ctrl + Shift + G`): רשימת קבצים, והשוואה צד-לצד בלחיצה. הכי נוח לעין, כמו שלמדנו בפרק 5.

**2. הפקודה `/diff` בתוך Claude Code**: מציגה את כל השינויים בתיקייה, כולל אלה שClaude עשה בשיחה הנוכחית.

```text title="בתוך Claude Code"
/diff
```

**3. לבקש מ-Claude סיכום**, וזו הדרך הכי שימושית כשיש הרבה שינויים:

<Prompt>תשווה את הענף הנוכחי ל-main, ותסכם לי: אילו קבצים השתנו, מה הפיצ'ר עושה עכשיו, ומה יכול להישבר בגלל השינויים האלה. תהיה כן, גם אם זה קוד שאתה כתבת</Prompt>

ככה נראה diff גולמי, למקרה שתרצו להציץ:

```diff title="git diff main (פלט לדוגמה)"
--- a/components/RecipeCard.tsx
+++ b/components/RecipeCard.tsx
@@ -12,6 +12,10 @@ export function RecipeCard({ recipe }: Props) {
       <h3 className="text-xl font-bold">{recipe.title}</h3>
+      <FavoriteButton slug={recipe.slug} />
       <p className="text-gray-600">{recipe.time} דקות</p>
-      <span>{recipe.category}</span>
+      <span className="rounded-full px-3">{recipe.category}</span>
```

שורות עם `+` נוספו, שורות עם `-` נמחקו. השורות בלי סימן הן הקשר, כדי שתבינו איפה זה קורה.

## חלק 5: Pull Requests וסקירת קוד

### מה זה Pull Request, ולמה צריך אותו אם עובדים לבד?

Pull Request (או PR) הוא בקשה רשמית: "הנה ענף עם שינויים, אני מציע לאחד אותו לתוך main". ב-GitHub הוא מקבל דף משלו, עם תיאור, עם כל השינויים ועם מקום להערות.

גם כשעובדים לבד, PR הוא עצירה מכוונת לפני שמשהו נכנס לגרסה הרשמית: מקום לסקור, להריץ בדיקות ולחשוב פעם נוספת. ובפרק 9, כשהאתר יהיה מחובר ל-Vercel, כל PR יקבל גם **כתובת תצוגה מקדימה** משלו, ותוכלו לראות את השינוי באוויר לפני שהוא מגיע לאתר האמיתי.

### התהליך המלא

| # | שלב | הפקודה שתראו |
| --- | --- | --- |
| 1 | ענף חדש מתוך main | `git switch -c feature/favorites` |
| 2 | עבודה ושמירות, כמה פעמים | `git commit` |
| 3 | דחיפת הענף ל-GitHub | `git push -u origin feature/favorites` |
| 4 | פתיחת PR | `gh pr create` |
| 5 | סקירה ותיקונים | `/code-review`, ועוד שמירות לפי הצורך |
| 6 | מיזוג ל-main | כפתור **Merge** ב-GitHub |
| 7 | עדכון main במחשב | `git switch main` ואז `git pull` |

לא צריך להקליד אף אחת מהפקודות האלה. הן כאן כדי שתזהו אותן בבקשות האישור של Claude.

/>

### סקירת קוד: Claude בודק את Claude

הנה שלוש דרכים לקבל סקירה, מהפשוטה לרשמית:

**1. בקשה רגילה, בשיחה חדשה.** אחרי `/clear`, Claude מסתכל על השינויים בעיניים רעננות, בלי להיות קשור לקוד שהוא עצמו כתב:

<Prompt>תסקור את השינויים בענף הנוכחי לעומת main כמו מפתח בכיר וקפדן. תחפש באגים, מקרי קצה שלא טופלו, בעיות נגישות ובעיות בתצוגה בטלפון. תציג רשימה לפי חומרה, עם הפניה לקובץ ולשורה, ועוד בלי לתקן</Prompt>

**2. הפקודה המובנית `/code-review`** (או בקיצור `/review`): סוקרת את השינויים הנוכחיים ומחפשת באגים, בסוכן נפרד עם הקשר נקי.

```text title="בתוך Claude Code"
/code-review
```

אפשר גם לסקור PR לפי המספר שלו, למשל `/code-review 3`, ולהוסיף `--comment` כדי שההערות יפורסמו ישירות ב-PR ב-GitHub.

**3. סקירת אבטחה עם `/security-review`**: בודקת את השינויים בענף מול main ומחפשת בעיות אבטחה, כמו מידע רגיש שנחשף או קלט שלא נבדק. מומלץ במיוחד לפני מיזוג של כל דבר שקשור לטפסים, להתחברות או לשמירת מידע.

```text title="בתוך Claude Code"
/security-review
```

אחרי הסקירה, מחליטים מה לתקן:

<Prompt>תתקן את הבעיות ברמת חומרה גבוהה ובינונית מהסקירה, תשמור כל תיקון בשמירה נפרדת עם הודעה ברורה, ותדחוף לאותו ענף. ה-PR יתעדכן לבד</Prompt>

<Callout type="tip" title="למתקדמים: Claude בתוך GitHub">
הפקודה `/install-github-app` מתקינה את אפליקציית Claude ב-GitHub עבור המאגר שלכם. אחרי ההתקנה אפשר לכתוב `@claude` בתגובה על PR או על Issue ב-GitHub, ו-Claude יענה, יסקור או יתקן ישירות שם. זה שימושי במיוחד כשעובדים בצוות.
</Callout>

### ממזגים

את המיזוג **עשו בעצמכם**, ב-GitHub: פתחו את דף ה-PR, עברו על הלשונית **Files changed** כדי לראות את כל השינויים, ואם הכול טוב, לחצו **Merge pull request** ואז **Confirm merge**.

<Callout type="note" title="למה לא לתת ל-Claude למזג?">
הוא יכול, עם `gh pr merge`. אבל המיזוג ל-main הוא בדיוק הרגע שבו כדאי שבן אדם יחליט. לחיצה אחת בדפדפן אחרי מבט אחרון היא ההרגל הבריא.
</Callout>

אחרי המיזוג, מעדכנים את המחשב:

<Prompt>מיזגתי את ה-PR ב-GitHub. תחזור ל-main, תמשוך את העדכונים מ-GitHub, ותמחק את הענף המקומי feature/favorites כי הוא כבר מוזג</Prompt>

## חלק 6: חגורות בטיחות

Git הוא רשת ביטחון מצוינת, אבל יש כמה פקודות שיכולות לקרוע בה חורים. הנה אילו, ואיך בונים הגנה בכמה שכבות.

### הפקודות שצריך להכיר (כדי לא לאשר אותן)

| פקודה | מה היא עושה | למה זה מסוכן |
| --- | --- | --- |
| `git push --force` (או `-f`) | דוחפת ודורסת את מה שיש ב-GitHub | מוחקת מ-GitHub שמירות שלא קיימות אצלכם, למשל עבודה של מישהו אחר או שמירות ממחשב אחר |
| `git reset --hard` | מחזירה את התיקייה לשמירה קודמת | כל שינוי שלא נשמר נמחק, בלי אפשרות שחזור |
| `git clean -fd` | מוחקת קבצים ש-Git לא מכיר | קבצים חדשים שעוד לא נשמרו נמחקים לגמרי |
| `git checkout -- .` / `git restore .` | מבטלת את כל השינויים שלא נשמרו | עבודה שלא נשמרה הולכת לאיבוד |
| `git branch -D` | מוחקת ענף גם אם לא מוזג | עבודה שנשמרה רק בענף הזה עלולה ללכת לאיבוד |
| `git commit --amend` אחרי push | משכתבת שמירה שכבר עלתה | ההיסטוריה המקומית וזו שב-GitHub מתפצלות, ואז "צריך" force push |

<Callout type="warning" title="הכלל הפשוט">
אם בבקשת אישור מופיעות המילים **force**, **hard**, **clean**, **-D** או **amend**, עצרו. בחרו **No** ושאלו את Claude: "למה צריך את הפקודה הזאת, ומה יקרה אם נשתמש בה? יש דרך בטוחה יותר?". כמעט תמיד יש.
</Callout>

### שכבה 1: העיניים שלכם

ב**מצב ידני** (manual), כל פקודה עוברת דרככם, ואתם קוראים לפני שמאשרים, בדיוק כמו בפרק 3.

ב**מצב אוטומטי** (auto), מנגנון הבטיחות של Claude Code חוסם כברירת מחדל פקודות מסוכנות כמו force push, `git reset --hard` ו-`git clean -fd`. בנוסף, הוא מתייחס לגבולות שאתם מציבים בשיחה. אם תכתבו "אל תדחוף ל-GitHub בלי לשאול אותי", המנגנון יחסום דחיפות עד שתגידו אחרת.

### שכבה 2: כללים ב-CLAUDE.md

```markdown title="CLAUDE.md"
## Git
- אף פעם לא git push --force, ואף פעם לא push ישירות ל-main.
- כל פיצ'ר בענף משלו, ומיזוג ל-main רק דרך Pull Request.
- לפני פקודה שמוחקת שינויים (reset, clean, restore), תעצור ותשאל.
- הודעות commit באנגלית, שורה ראשונה קצרה שמתארת מה ולמה.
```

זה משפיע מאוד על ההתנהגות של Claude, אבל זו **הנחיה, לא נעילה**. בשביל נעילה אמיתית צריך את השכבות הבאות.

### שכבה 3: חוקי הרשאות ב-Claude Code

בקובץ ההגדרות של הפרויקט אפשר לקבוע פקודות ש-Claude Code **חוסם תמיד** (`deny`), ופקודות שעליהן הוא **תמיד שואל** (`ask`), בכל מצב הרשאות, גם במצב האוטומטי:

```json title=".claude/settings.json"
{
  "permissions": {
    "deny": [
      "Bash(git push --force *)",
      "Bash(git push -f *)",
      "Bash(git push --force-with-lease *)",
      "Bash(git reset --hard *)",
      "Bash(git clean *)"
    ],
    "ask": [
      "Bash(git push *)"
    ]
  }
}
```

- **`deny`**: הפקודות האלה ייחסמו, נקודה.
- **`ask`**: כל `git push` אחר יבקש את אישורכם, גם במצב אוטומטי.

אפשר גם לבקש מ-Claude ליצור את הקובץ:

<Prompt>תיצור קובץ .claude/settings.json בפרויקט, עם חוקי הרשאות שחוסמים את git push --force, git push -f, git reset --hard ו-git clean, ושמבקשים אישור לפני כל git push אחר. תסביר לי כל שורה</Prompt>

ואת החוקים הקיימים אפשר לראות ולערוך בכל רגע עם הפקודה `/permissions`.

<Callout type="info" title="איפה שמים את הקובץ?">
`.claude/settings.json` בתיקיית הפרויקט חל על כל מי שעובד על הפרויקט, ונשמר ב-Git יחד עם הקוד. `~/.claude/settings.json` בתיקיית הבית חל עליכם בכל הפרויקטים. את חוקי הבטיחות של Git כדאי לשים **בשניהם**.
</Callout>

<Callout type="warning" title="למה צריך עוד שכבה?">
החוקים האלה בודקים את **הטקסט** של הפקודה. פקודה שכתובה קצת אחרת, למשל `git -C . push --force`, עלולה לא להתאים לתבנית. זו שכבה חזקה, אבל לא מושלמת. השכבה הבאה לא תלויה בניסוח בכלל.
</Callout>

### שכבה 4: הגנה על main ב-GitHub

זו השכבה החזקה ביותר, כי היא נאכפת **בשרת של GitHub**. לא משנה מי שולח את הפקודה ואיך היא מנוסחת: Claude, אתם, או כל אחד אחר.

בדף המאגר ב-GitHub:

1. לחצו על **Settings** (בתפריט העליון של המאגר).
2. בתפריט הצד, תחת **Code and automation**, בחרו **Rules → Rulesets**.
3. לחצו **New ruleset → New branch ruleset**.
4. תנו שם, למשל `protect-main`, ושנו את **Enforcement status** ל-**Active**.
5. תחת **Target branches** לחצו **Add target → Include default branch**.
6. סמנו את החוקים:
   - **Restrict deletions**: אי אפשר למחוק את main.
   - **Block force pushes**: אי אפשר לדרוס את main.
   - **Require a pull request before merging**: שינויים נכנסים ל-main רק דרך PR.
7. לחצו **Create**.

מעכשיו, אם מישהו ינסה לדחוף בכוח ל-main, GitHub יסרב:

```text title="ניסיון force push ל-main מוגן (פלט לדוגמה)"
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Cannot force-push to this branch
 ! [remote rejected] main -> main (push declined due to repository rule violations)
```

<Callout type="note" title="שימו לב לסוג המאגר">
בחשבון GitHub חינמי, ההגנה על ענפים זמינה במאגרים **ציבוריים**. במאגרים **פרטיים** היא דורשת בדרך כלל חשבון בתשלום (כמו GitHub Pro). אם המאגר שלכם פרטי והאפשרות לא זמינה, שכבות 1 עד 3 עדיין מגינות עליכם היטב.
</Callout>

### ואם בכל זאת משהו נמחק?

Git כמעט אף פעם לא שוכח באמת. גם אחרי `reset` או מחיקת ענף, שמירות ישנות נשארות זמן מה ביומן פנימי שנקרא **reflog**. אם קרה משהו:

<Prompt>נראה לי שאיבדתי שמירות. אל תשנה כלום עדיין. תשתמש ב-git reflog כדי למצוא את המצב לפני הפעולה האחרונה, ותסביר לי מה אתה רואה ואיך מומלץ לשחזר</Prompt>

שימו לב ל"אל תשנה כלום עדיין": במצב חירום, הדבר הראשון הוא להבין, ורק אחר כך לפעול.

## סיכום

- **Git** שומר נקודות שמירה, ו-**GitHub** שומר אותן בענן. לא צריך לזכור פקודות: מבקשים מ-Claude, ומבינים מה מאשרים.
- **שמירות טובות**: נושא אחד בכל שמירה, עם הודעה שמסבירה מה ולמה.
- **ענפים** לכל פיצ'ר או ניסוי. main נשאר נקי.
- **לראות מה השתנה**: Source Control ב-Cursor, `/diff`, או סיכום מ-Claude.
- **Pull Request**: ענף ← PR עם תיאור ← `/code-review` ו-`/security-review` ← מיזוג שאתם עושים בעצמכם.
- **ארבע שכבות בטיחות**: העיניים שלכם, CLAUDE.md, חוקי `deny`/`ask` ב-`.claude/settings.json`, והגנה על main ב-GitHub.

בפרק הבא נעלה את האתר לאוויר ב-Vercel: כל דחיפה ל-main תעדכן את האתר אוטומטית, וכל Pull Request יקבל כתובת תצוגה מקדימה משלו.
