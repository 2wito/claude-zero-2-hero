# איתור ותיקון באגים אוטומטי

באגים הם לא סימן שעשיתם משהו לא בסדר. הם חלק רגיל מכל פרויקט, גם אצל המפתחים הכי מנוסים בעולם. ההבדל בין מתחיל למקצוען הוא לא כמה באגים יש, אלא **כמה מהר מוצאים ומתקנים אותם**.

כאן Claude Code באמת זורח. הוא יודע לקרוא הודעות שגיאה מפחידות, לעקוב אחרי הבעיה דרך כמה קבצים, למצוא את המקור ולתקן אותו. התפקיד שלכם: לתת לו את הרמזים הנכונים, לוודא שהוא מתקן את **הבעיה** ולא רק מסתיר אותה, ולדעת לחזור אחורה כשמשהו לא הצליח.

<Callout type="note" title="מה תלמדו בפרק">
- לקרוא הודעת שגיאה, ולהעביר אותה ל-Claude בצורה הכי יעילה.
- לגרום ל-Claude למצוא את **שורש הבעיה**, גם כשהיא מפוזרת על כמה קבצים.
- לבטל תיקון שהזיק, עם `/rewind` או עם Git.
- לחשוב על מקרי קצה לפני שהמשתמשים ימצאו אותם.
- לתקן שגיאות בנייה של `npm run build`.
</Callout>

## אנטומיה של הודעת שגיאה

הודעת שגיאה נראית כמו ג'יבריש, אבל יש לה מבנה קבוע. הנה שגיאה טיפוסית מפרויקט Next.js:

```text title="שגיאה לדוגמה"
TypeError: Cannot read properties of undefined (reading 'map')
    at RecipePage (app/recipes/[slug]/page.tsx:24:38)
    at renderWithHooks (node_modules/react-dom/cjs/react-dom-server.js:1523:18)
    at renderElement (node_modules/react-dom/cjs/react-dom-server.js:2104:9)
```

| חלק | בדוגמה | מה הוא אומר |
| --- | --- | --- |
| **סוג השגיאה** | `TypeError` | איזו קטגוריה של בעיה. TypeError אומר בדרך כלל "ניסיתי להשתמש במשהו שהוא לא מה שחשבתי" |
| **ההודעה** | `Cannot read properties of undefined (reading 'map')` | מה קרה: ניסו להריץ `map` על משהו שלא קיים (`undefined`) |
| **המיקום** | `page.tsx:24:38` | הקובץ, השורה (24) והתו (38) שבהם זה קרה |
| **מחסנית הקריאות** (Stack Trace) | כל שורות ה-`at` | המסלול שהקוד עבר עד שנפל, מהמקום הכי קרוב לבעיה ועד הרחוק ביותר |

<Callout type="tip" title="לא חייבים להבין, אבל חייבים להעתיק">
לא צריך לפענח את השגיאה בעצמכם. זו העבודה של Claude. אבל צריך להעביר לו **את כל השגיאה**. שורות שנראות לכם לא חשובות, כמו שורות `at` שמפנות ל-`node_modules`, עוזרות לו להבין את ההקשר.
</Callout>

**2. מריצים את הפקודה בתוך Claude Code, עם `!`.** במקום להריץ בחלון אחר ולהעתיק, מריצים ישירות בשיחה. הפלט, כולל השגיאות, נכנס לשיחה, ו-Claude רואה הכול:

## שלב 2: מוצאים את שורש הבעיה

### סימפטום מול סיבה

כשיש לכם חום, אפשר לקחת אקמול, והחום ירד. אבל אם יש דלקת, היא עדיין שם. גם בקוד: **המקום שבו השגיאה מופיעה הוא לא תמיד המקום שבו הבעיה נמצאת.**

בדוגמה שלנו, השגיאה מופיעה ב-`page.tsx`, בשורה שמציגה את המצרכים:

```tsx title="app/recipes/[slug]/page.tsx"
<ul>
  {recipe.ingredients.map((item) => (
    <li key={item.name}>{item.amount} {item.unit} {item.name}</li>
  ))}
</ul>
```

הקוד הזה תקין לגמרי. הבעיה נמצאת **בקובץ אחר**: הטופס להוספת מתכון שומר את המצרכים תחת שם אחר:

```ts title="app/add/actions.ts"
const newRecipe = {
  title: formData.get("title"),
  slug: makeSlug(formData.get("title")),
  ingredientsList: parseIngredients(formData.get("ingredients")), // ← השם לא תואם
  steps: parseSteps(formData.get("steps")),
};
```

מתכונים מהטופס נשמרים עם `ingredientsList`, ודף המתכון מחפש `ingredients`. אצלו, השדה פשוט לא קיים, כלומר `undefined`, ומשם הקריסה.

שימו לב: כדי למצוא את זה צריך לעקוב אחרי הנתונים **דרך כמה קבצים**: הטופס, קובץ השמירה, קובץ ה-JSON ודף המתכון. זה בדיוק מה ש-Claude עושה טוב, אם מבקשים ממנו.

### מבקשים חקירה, לא תיקון

<PromptCompare
  bad="תתקן את השגיאה ב-page.tsx"

<Callout type="tip" title="מצב תכנון הוא מצב חקירה מושלם">
לחצו `Shift + Tab` עד `plan mode on`. במצב הזה Claude יכול לקרוא, לחפש ולהריץ פקודות שרק בודקות, אבל לא לשנות קבצים. זה מבטיח שהחקירה נשארת חקירה, ושאף "תיקון" לא נכנס לפני שהבנתם מה קורה.
</Callout>

### עוד טכניקות חקירה

**היפותזות מדורגות.** כשהבעיה לא ברורה, בקשו מ-Claude לחשוב כמו בלש:

<Prompt>תציע שלוש סיבות אפשריות לבעיה, מהסבירה ביותר לפחות סבירה. לכל אחת: איך נבדוק אם היא נכונה, בלי לשנות קוד</Prompt>

**מה השתנה?** אם משהו עבד אתמול ולא עובד היום, התשובה נמצאת כמעט תמיד בשינויים האחרונים. כאן Git (פרק 8) משתלם:

<Prompt>הדף הזה עבד בשמירה של אתמול ונשבר מאז. תשווה את הקוד הנוכחי לשמירות האחרונות ב-git, ותגיד לי איזה שינוי הכי סביר שגרם לבעיה</Prompt>

**הדפסות זמניות.** לפעמים צריך לראות מה קורה בזמן ריצה:

<Prompt>תוסיף הדפסות זמניות (console.log) במקומות המרכזיים בדרך של הנתונים, כדי שנראה איפה הם משתנים. תסמן כל הדפסה בהערה TEMP-DEBUG, כדי שיהיה קל למחוק את כולן אחרי שנמצא את הבעיה</Prompt>

**חקירה בפרויקט גדול.** אם צריך לחפש בהרבה קבצים, אפשר לבקש מ-Claude להשתמש ב**סוכני משנה** (Subagents). הם קוראים את הקבצים בחלון הקשר נפרד ומחזירים רק את המסקנות, כך שהשיחה הראשית לא מתמלאת:

<Prompt>תשתמש בסוכני משנה כדי לחקור את כל המקומות בפרויקט שבהם נשמרים או נקראים מתכונים, ותחזיר לי רשימה של כל שמות השדות שבשימוש בכל מקום</Prompt>

## שלב 3: מתקנים ומוודאים

### תיקון אמיתי מול טיוח

אחרי שהבנתם את שורש הבעיה, מבקשים תיקון, ומקפידים שהוא יטפל **בסיבה**:

<Prompt>עכשיו תתקן את שורש הבעיה: תאחד את שם השדה כך שהטופס ישמור ingredients, כמו כל שאר המתכונים. תתקן גם מתכונים שכבר נשמרו בשם הישן בקובץ ה-JSON. בנוסף, תוסיף לדף המתכון הודעה ידידותית אם למתכון אין מצרכים בכלל, במקום קריסה</Prompt>

```diff title="app/add/actions.ts: התיקון"
-  ingredientsList: parseIngredients(formData.get("ingredients")),
+  ingredients: parseIngredients(formData.get("ingredients")),
```

<Callout type="warning" title="דגלים אדומים: תיקונים שמסתירים את הבעיה">
כשאתם בודקים את התיקון של Claude, היזהרו מכל אחד מאלה. כולם גורמים לשגיאה **להיעלם** בלי לפתור את הבעיה:

- **`try / catch` שבולע שגיאות** בלי לטפל בהן: השגיאה עדיין קורית, רק שקט.
- **`// @ts-ignore`** או **`as any`**: מכבים את בדיקת הטיפוסים של TypeScript בדיוק במקום שבו היא מצאה בעיה.
- **`// eslint-disable`**: מכבים את בודק הקוד.
- **מחיקה או השבתה של בדיקה (Test)** שנכשלת.
- **`?.` או `|| []` על כל דבר**: לפעמים זה נכון, אבל אם זה כל התיקון, כנראה שהנתונים עדיין שגויים.

ראיתם אחד מאלה? שאלו: "זה מתקן את שורש הבעיה או רק מסתיר אותה?"
</Callout>

הכי פשוט לכתוב את זה מראש בבקשה:

<PromptCompare
  bad="תגרום לשגיאה להיעלם"
  good="תתקן את שורש הבעיה. אל תסתיר את השגיאה עם try/catch, ts-ignore או בדיקות שמדלגות על המקרה. אם אתה חושב שאין ברירה אלא לעקוף, תעצור ותסביר לי למה."
  why="״להיעלם״ זו מטרה שאפשר להשיג גם בטיוח. ״שורש הבעיה״ עם רשימת האיסורים מבהירה מה נחשב תיקון אמיתי."
/>

### קודם משחזרים, אחר כך מתקנים

הדרך הכי בטוחה לדעת שבאג תוקן: **לראות אותו קורה, לתקן, ולראות שהוא כבר לא קורה.**

<Prompt>לפני שאתה מתקן, תכתוב בדיקה (Test) קטנה שמשחזרת את הבאג ונכשלת. אחר כך תתקן, ותריץ את הבדיקה שוב כדי להראות שהיא עוברת. תראה לי את הפלט של שתי ההרצות</Prompt>

אם בפרויקט אין עדיין בדיקות אוטומטיות, אפשר לבקש גרסה פשוטה יותר:

<Prompt>תכתוב לי רשימה של צעדים מדויקים לשחזר את הבאג בדפדפן. אני אוודא שהוא קורה, ואחרי התיקון אבדוק שוב לפי אותם צעדים</Prompt>

### כלל השניים

אם Claude ניסה לתקן **פעמיים** ועדיין לא הצליח, אל תמשיכו לבקש "תנסה שוב". השיחה כבר מלאה בניסיונות כושלים, והם מבלבלים אותו. במקום זה:

1. חזרו אחורה לפני הניסיונות הכושלים (בחלק הבא).
2. הריצו `/clear`.
3. כתבו בקשה חדשה שכוללת את **מה שלמדתם**: "כבר ניסינו X ו-Y וזה לא עבד, כי Z".

## שלב 4: כשהתיקון הזיק, חוזרים אחורה

לפעמים "תיקון" שובר משהו אחר, או ש-Claude שינה יותר ממה שביקשתם. אין בעיה: יש כמה דרכים לחזור אחורה, לכל מצב הדרך שלו.

### עצירה מיידית: `Esc`

רואים ש-Claude הולך לכיוון לא נכון? `Esc` אחד עוצר אותו מיד. השיחה נשמרת, ואפשר להסביר לו מה לעשות אחרת.

### חזרה בזמן: `/rewind`

Claude Code שומר **נקודת ביקורת** (Checkpoint) לפני כל הודעה שאתם שולחים, כולל עותק של הקבצים שהוא עומד לשנות. כדי לחזור:

```text title="בתוך Claude Code"
/rewind
```

או לחיצה כפולה על `Esc`. ייפתח תפריט של ההודעות הקודמות שלכם. בוחרים את הנקודה שאליה רוצים לחזור, ואז בוחרים **מה** להחזיר:

| אפשרות | מה קורה | מתי להשתמש |
| --- | --- | --- |
| **קוד ושיחה** | גם הקבצים וגם השיחה חוזרים לנקודה שבחרתם | ה"תיקון" היה טעות מוחלטת, ורוצים להתחיל מחדש מאותה נקודה |
| **רק קוד** | הקבצים חוזרים, השיחה נשארת | רוצים לבטל את השינויים, אבל ש-Claude יזכור מה ניסה ולמה זה לא עבד |
| **רק שיחה** | השיחה חוזרת, הקבצים נשארים | הקוד בסדר, אבל השיחה הסתבכה וצריך להתחיל ממנה מחדש |
| **סיכום מנקודה זו** | ההודעות מהנקודה הזאת מסוכמות | השיחה ארוכה, ורוצים לפנות מקום בלי לאבד את מה שהיה |

<Callout type="tip" title="נקודות הביקורת לא נעלמות כשסוגרים">
נקודות הביקורת נשמרות יחד עם השיחה. אפשר לסגור את הטרמינל, לחזור לשיחה מחר עם `claude -c`, ועדיין לחזור אחורה.
</Callout>

<Callout type="warning" title="מה /rewind לא יכול להחזיר">
נקודות הביקורת עוקבות **רק אחרי קבצים ש-Claude ערך בכלי העריכה שלו**. הן לא מבטלות:

- **פקודות טרמינל**: התקנת חבילות (`npm install`), מחיקת קבצים (`rm`), פעולות Git.
- **פעולות מחוץ למחשב**: דחיפה ל-GitHub, שליחת טופס, שינוי במסד נתונים.
- **שינויים שעשיתם בעצמכם** ב-Cursor.

בשביל אלה צריך את Git.
</Callout>

### חזרה עם Git

Git הוא רשת הביטחון החזקה ביותר, כי הוא שומר את **כל** מצב הפרויקט ולא משנה מי שינה אותו. אם שמרתם נקודת ביטחון לפני שהתחלתם לתקן (פרק 8), אתם תמיד יכולים לחזור אליה.

**ביטול שינויים שעוד לא נשמרו בקובץ מסוים:**

<Prompt>תראה לי מה השתנה ב-app/page.tsx מאז השמירה האחרונה ב-git. אם זה רק התיקון הכושל, תחזיר את הקובץ הזה בלבד למצב של השמירה האחרונה</Prompt>

```bash title="מה Claude יריץ (לדוגמה)"
git diff app/page.tsx
git restore app/page.tsx
```

<Callout type="warning" title="git restore מוחק שינויים שלא נשמרו">
`git restore` מחזיר קובץ למצב של השמירה האחרונה, וכל שינוי שלא נשמר בו נמחק. לכן קודם מסתכלים על ה-diff, ורק אחר כך מאשרים. ולעולם לא `git restore .` (עם נקודה) או `git reset --hard` בלי לדעת בדיוק מה ימחק. אלה מוחקים את **כל** השינויים בכל הפרויקט.
</Callout>

**ביטול שמירה שכבר נעשתה:**

<Prompt>השמירה האחרונה ב-git שברה את החיפוש. תבטל אותה עם git revert, כך שתיווצר שמירה חדשה שמבטלת אותה, בלי למחוק היסטוריה</Prompt>

```bash title="מה Claude יריץ (לדוגמה)"
git log --oneline -3
git revert a3f9c21
```

`git revert` לא מוחק את השמירה הבעייתית. הוא מוסיף שמירה **חדשה** שמבטלת אותה, ולכן הוא בטוח גם אחרי שהקוד כבר עלה ל-GitHub.

### איזה כלי מתי?

| המצב | הכלי |
| --- | --- |
| Claude באמצע, והולך לכיוון לא נכון | `Esc` |
| Claude ערך קבצים בשיחה הזאת, והעריכה הזיקה | `/rewind` (או `Esc` פעמיים) |
| השינוי כולל פקודות טרמינל, או שעשיתם שינויים בעצמכם | Git: `git restore` לקובץ מסוים, אחרי בדיקת diff |
| השינוי כבר נשמר ב-git | `git revert` |
| השינוי כבר עלה ל-GitHub | `git revert`, ואז דחיפה רגילה. אף פעם לא force push (פרק 8) |

## שלב 5: מקרי קצה, הבאגים שעוד לא קרו

**מקרה קצה** (Edge Case) הוא מצב לא שגרתי שהקוד לא תמיד מוכן אליו: שדה ריק, מספר אפס, טקסט ארוך מאוד, אינטרנט איטי. רוב הבאגים שמשתמשים אמיתיים מוצאים הם בדיוק כאלה. הדרך הכי טובה לטפל בהם: למצוא אותם **לפני** המשתמשים.

| סוג | דוגמה באתר המתכונים | מה עלול לקרות |
| --- | --- | --- |
| **ריק** | חיפוש שמכיל רק רווחים | כל המתכונים נעלמים, או שאף אחד לא נעלם |
| **אפס או שלילי** | מחשבון מנות על 0 | חלוקה באפס, כמויות `NaN` |
| **חסר** | מתכון בלי אימוג'י או בלי שלבים | חור בעיצוב, או קריסה |
| **ארוך מאוד** | שם מתכון של 80 תווים | הטקסט חורג מהכרטיס |
| **תווים מיוחדים** | שם עם גרשיים: "פשטידת ג'ינג'ר" | שבירה בקישור או בחיפוש |
| **עברית ואנגלית מעורבות** | "עוגת Oreo של שירה" | סדר מילים הפוך |
| **אחסון לא זמין** | גלישה בחלון פרטי | המועדפים או סימון השלבים קורסים |

## שלב 6: תיקון שגיאות בנייה (npm run build)

### למה זה עובד ב-dev ונשבר ב-build?

`npm run dev` סלחני: הוא מריץ את האתר גם כשיש בעיות קטנות, כדי שתוכלו להמשיך לעבוד. `npm run build` מכין את הגרסה שתעלה לאוויר, והוא **קפדני**: הוא בודק את כל הקבצים, את הטיפוסים של TypeScript, ולפעמים גם מריץ בודק קוד (Lint). לכן לא נדיר שהאתר עובד מצוין ב-dev, ונכשל ב-build.

**הכלל:** מריצים `npm run build` לעתים קרובות, לא רק רגע לפני ההעלאה. ככה כל בעיה קטנה ופשוטה לתיקון.

### השגיאות הנפוצות

**שגיאת טיפוסים** (Type error): הקוד מעביר ערך מסוג אחד למקום שמצפה לסוג אחר.

```text title="פלט לדוגמה"
./components/ServingsCalculator.tsx:14:7
Type error: Type 'string' is not assignable to type 'number'.

  12 |   const [servings, setServings] = useState(recipe.servings);
  13 |   function onChange(e) {
> 14 |     setServings(e.target.value);
     |                 ^
```

כאן הערך מתיבת הקלט הוא טקסט (`"4"`), והקוד מצפה למספר (`4`).

**מודול לא נמצא** (Module not found): קובץ או חבילה שהקוד מנסה לייבא לא קיימים, בדרך כלל בגלל שם שגוי, אות גדולה או קטנה, או חבילה שלא הותקנה.

```text title="פלט לדוגמה"
Module not found: Can't resolve '@/components/recipeCard'
```

(שימו לב: הקובץ נקרא `RecipeCard`, עם R גדולה. ב-Windows זה לפעמים עובד ב-dev, ונשבר רק בבנייה או בשרת.)

**רכיב של צד הלקוח בלי הצהרה**: קוד שמשתמש ביכולות של הדפדפן, כמו `useState` או לחיצות, בלי לסמן את הקובץ כ-Client Component:

```text title="פלט לדוגמה"
You're importing a component that needs `useState`. This React Hook only works
in a Client Component. To fix, mark the file (or its parent) with the
`"use client"` directive.
```

**שגיאה ביצירת דף מראש** (Prerender error): הבנייה מנסה ליצור דף מראש, ומשהו בו קורס. בדרך כלל זו בעיה בנתונים, כמו בדוגמת `ingredients` שראינו.

```text title="פלט לדוגמה"
Error occurred prerendering page "/recipes/grandma-cheesecake".
TypeError: Cannot read properties of undefined (reading 'map')
```

### הלולאה: לבנות, לתקן, לחזור

<Prompt>תריץ npm run build. אם יש שגיאות, תתקן את שורש הבעיה של כל אחת, ותריץ שוב. תחזור על זה עד שהבנייה עוברת בלי שגיאות. אסור להשבית בדיקות כדי לעבור: בלי ts-ignore, בלי eslint-disable, ובלי לשנות הגדרות כדי להתעלם משגיאות. בסוף תראה לי את הפלט הסופי, ותסכם במשפט אחד כל תיקון שעשית</Prompt>

<Callout type="warning" title="הדגל האדום הכי גדול: לכבות את הבדיקות">
ב-Next.js יש הגדרות שגורמות לבנייה **להתעלם** משגיאות. אם אתם רואים ש-Claude מוסיף משהו כזה ל-`next.config`, עצרו:

```ts title="next.config.ts: לא לאשר!"
const nextConfig = {
  typescript: { ignoreBuildErrors: true }, // ← מסתיר את כל שגיאות הטיפוסים
};
```

זה כמו לנתק את נורית "בדוק מנוע" ברכב במקום לתקן את המנוע. הבנייה תעבור, והבאגים יגיעו לאתר שבאוויר.
</Callout>

<Callout type="note" title="שגיאה מוזרה שלא מסתדרת?">
לפעמים הבעיה היא לא בקוד, אלא בקבצים זמניים ששמורים מבנייה קודמת. בקשו מ-Claude: "תמחק את תיקיית .next ותריץ build מחדש". זו תיקייה שנבנית מחדש בכל פעם, ולכן מותר למחוק אותה.
</Callout>

## סיכום

- **מעבירים שגיאה בשלמותה**: העתק-הדבק, `!` בתוך Claude Code, `2>&1 | claude -p`, או צילום מסך. עם דוח באג: מה עשיתי, מה ציפיתי, מה קרה, מאז מתי.
- **קודם חקירה, אחר כך תיקון**: מצב תכנון, מעקב אחרי הנתונים דרך כל הקבצים, היפותזות, ובדיקה מה השתנה ב-git.
- **תיקון אמיתי, לא טיוח**: בלי `try/catch` שבולע, בלי `ts-ignore` ובלי לכבות בדיקות. משחזרים את הבאג, מתקנים, ומוודאים.
- **חזרה אחורה**: `Esc` לעצירה, `/rewind` לעריכות של Claude, `git restore` ו-`git revert` לכל השאר.
- **מקרי קצה**: ריק, אפס, חסר, ארוך, תווים מיוחדים. מוצאים אותם לפני המשתמשים.
- **שגיאות בנייה**: מריצים `npm run build` לעתים קרובות, ומתקנים בלולאה עד שעובר.
